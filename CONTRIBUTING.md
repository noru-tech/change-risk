# Contributing

Thanks for helping. Bugs, signal adapters and specification changes are all welcome; open an issue
first for anything that changes how a tier is derived.

## Ground rules

- **Deterministic.** `evaluate` never reads the network, the clock, the environment or `git`. The
  same facts give the same bytes.
- **The base revision rule is not negotiable.** The map and the policy come from the target branch.
  Nothing a change contains may lower the requirements it is held to.
- **No content analysis and no model** in the derivation.
- **Every derivation change comes with a conformance vector**, and its `expected` is reviewed, not
  only regenerated.
- **Minimal dependencies**, pure Rust.

## Layout

| Path | What |
| --- | --- |
| `spec/change-risk.md` | The specification |
| `schemas/` | JSON Schemas, embedded in the binary |
| `src/evaluate.rs` | The derivation |
| `src/collect/` | git, GitHub and GitLab |
| `src/signals.rs` | Signal adapters |
| `src/output.rs`, `src/compile.rs`, `src/population.rs` | Outputs |
| `conformance/` | The corpus and its runner |
| `action.yml`, `templates/` | GitHub Action and GitLab component |

## Checks

```bash
cargo fmt --all
cargo clippy --all-targets --all-features -- -D warnings
cargo test
python3 conformance/run.py --verifier "target/debug/crisk -q evaluate -f json"
```

`UPDATE_CORPUS=1 cargo test --test conformance` regenerates the corpus expectations, and
`UPDATE_ASSETS=1 cargo test --test assets` the committed completions and man pages.

## Releases

Bump the version in `Cargo.toml`, update `CHANGELOG.md`, merge to `main`, then tag `vX.Y.Z` on
`main` and push the tag. `release.yml`, generated by cargo-dist from `dist-workspace.toml`:

1. builds the macOS and static Linux archives, the shell installer, the Homebrew formula and a
   CycloneDX SBOM;
2. attests them with GitHub artifact attestations;
3. creates the GitHub Release with every artifact attached;
4. pushes the formula to `noru-tech/homebrew-tap`;
5. publishes the `change-risk` crate to crates.io (`publish-crates.yml`, `cargo publish --locked`).

Prerelease tags (`vX.Y.Z-rc.1`) get a GitHub Release marked as a prerelease and skip Homebrew and
crates.io.

`release.yml` is never edited by hand. Change `dist-workspace.toml`, run `dist generate` (with
`allow-dirty` commented out, since it makes `dist generate` skip CI), restore `allow-dirty`, then
pin every action in `release.yml` back to a commit SHA. Custom publish jobs, such as
`publish-crates.yml`, are listed in `publish-jobs` and edited directly.

### One-time setup

- **Homebrew**: a `HOMEBREW_TAP_TOKEN` repository secret with `contents: write` on the tap.
- **crates.io**: the crate had to exist before trusted publishing could be configured, so 0.2.0 was
  published by hand with `cargo publish --locked`. Releases since then authenticate with crates.io
  trusted publishing (OIDC), not an API token. The trusted publisher is configured in the crate's
  settings on crates.io (Settings → Trusted Publishing → GitHub):
  - repository owner `noru-tech`, repository name `change-risk`;
  - workflow filename `release.yml`. crates.io matches the top-level workflow that triggered the
    run, not the reusable `publish-crates.yml` it calls;
  - environment: leave empty. If you later add a protected environment to the `crates-io` job in
    `publish-crates.yml`, enter the same name here.
